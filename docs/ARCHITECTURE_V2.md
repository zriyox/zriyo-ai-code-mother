## 一、设计目标

### 1.1 核心目标

构建一个 **通用 Agent 系统**，支持：
- **代码生成 + 一键部署**
- **文档分析** (DOCX、PDF、Excel)
- **数据可视化** (图表绘制)
- **BaaS 数据存储** (为生成的前端应用提供后端能力)

### 1.1.1 JoyAgent 参考架构

本架构参考了 **JoyAgent-JDGenie** 项目的成熟实践：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        JoyAgent 架构模式 (参考)                              │
│                                                                             │
│  ┌─────────────────────────────────────┐         ┌─────────────────────────┐│
│  │         Java 侧 (75%)               │         │      Python 侧 (25%)     ││
│  │                                     │         │                         ││
│  │  - Agent 编排 (AgentOrchestrator)   │◄────────┤  - Tool 服务 (REST API)  ││
│  │  - 意图识别 (IntentRecognizer)      │  HTTP   │  - 无状态执行           ││
│  │  - 任务路由 (TaskRouter)            │  + SSE  │  - 代码解释器           ││
│  │  - 配置管理 (ApiKeyManager)         │         │  - 报告生成器           ││
│  │  - 工具注册 (ToolRegistry)          │         │  - 深度搜索             ││
│  │  - Agent 循环 (Think → Act → Observe)│       │  - 数据分析             ││
│  │  - LLM 直接调用 (~200 行封装)       │         │  - 知识检索             ││
│  │                                     │         │                         ││
│  │  ❌ 不使用 LangChain4j              │         │  ❌ 不使用 LangChain    ││
│  └─────────────────────────────────────┘         └─────────────────────────┘│
└─────────────────────────────────────────────────────────────────────────────┘
```

**关键设计决策**：
| 决策点 | JoyAgent 模式 | 说明 |
|--------|---------------|------|
| **LangChain 使用** | ❌ 不使用 | JoyAgent 实践证明：直接调用 LLM API 仅需 ~200 行封装代码 |
| **Agent 编排位置** | ✅ Java 侧 | 意图识别、任务路由、Agent 循环、决策全部在 Java |
| **Python 角色** | 🔧 工具服务 | Python 只作为无状态 Tool 服务，通过 REST API 暴露能力 |
| **通信协议** | HTTP + SSE | Java POST 到 Python，Python SSE 流式返回结果 |
| **配置传递** | JWT Token | Java 创建 JWT 包含 API Key，Python 验证后提取配置 |
| **复杂度对比** | Java 主导 | Python 侧 25% 工具服务 vs Python 侧 Agent 6000+ 行复杂编排 |

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **Python 无状态** | Python 侧不存储任何密钥、Token、配置 |
| **Java 掌控配置** | 所有 API Key、模型配置由 Java 管理 |
| **Java 负责编排** | 意图识别、任务路由、Agent 切换均在 Java 侧 |
| **全链路追溯** | 每个事件都有 traceId，可完整追溯执行链路 |
| **可扩展性** | 新增能力只需添加 Agent 和 Tool，无需改架构 |
| **通用数据接口** | 为生成的前端应用提供 BaaS 数据存储能力 |
| **限流隔离** | 每个应用独立限流（默认 1 万条），互相隔离 |
| **错误重试** | 指数退避 + 幂等性 + SSE 断线恢复 |

## 二、当前架构分析

### 2.1 现状概览

当前项目采用 **Pipeline-Driven 架构**：

```
┌─────────────────────────────────────────────┐
│                    Java (Spring Boot)                   │
│                                                             │
│  用户请求 → Controller → Service → Pipeline → AI → 代码输出      │
│                       ↓             ↓          ↓              │
│                   业务逻辑     Handler    LangChain4j         │
└─────────────────────────────────────────────┘
```

### 2.2 技术栈

| 层次 | 技术 | 版本 |
|--------|------|--------|
| 框架 | Spring Boot | 3.5.4 |
| AI 框架 | LangChain4j | 1.1.0 |
| 语言 | Java | 21 |
| 数据库 | MySQL + Redis | - |
| ORM | MyBatis-Flex | 1.11.1 |

### 2.3 核心问题

| 问题 | 描述 | 影响 | JoyAgent 解决方案 |
|------|--------|------|-------------------|
| **LangChain4j 过旧** | 1.1.0 vs 最新 1.11.0 | 无法使用新特性 | ✅ **直接调用 LLM API**：无需 LangChain4j，~200 行封装代码 |
| **Java 职责过重** | AI 逻辑在 Java | 难以利用 Python 生态 | ✅ **Python 工具服务**：Python 作为无状态 Tool 服务暴露能力 |
| **无 Agent 能力** | 固定 Pipeline | 缺少自主决策 | ✅ **Java 侧 Agent 循环**：Think → Act → Observe，完全在 Java 实现 |
| **上下文管理低效** | 前3文件全量+截断 | Token 浪费严重 | ✅ **Java 侧统一管理**：基于 Token 预算的动态上下文压缩 |
| **无追溯能力** | 事件无 ID | 无法定位问题 | ✅ **TraceManager**：全链路 traceId 追溯 |
| **无数据接口** | 生成的前端应用无后端 | 无法存储业务数据 | ✅ **BaaS 服务**：为生成应用提供通用数据存储 |

**重要设计原则**：
- Python 侧**完全不存储**任何配置、密钥、Token
- 所有配置由 Java 侧通过 **JWT Token** 传入
- Python 侧只验证 JWT 签名，提取 API Key 后使用
- 每个 Tool 服务都是**无状态**的，可水平扩展

### 4.2 意图识别设计

#### 4.2.1 意图类型定义

```java
/**
 * 意图类型枚举
 */
public enum IntentType {
    // 代码相关
    CODE_GEN,           // 代码生成
    CODE_FIX,           // 代码修复
    CODE_EXPLAIN,        // 代码解释
    CODE_REFACTOR,      // 代码重构
    CODE_REVIEW,        // 代码审查

    // 文档相关
    DOC_ANALYZE,        // 文档分析
    DOC_SUMMARIZE,       // 文档摘要
    DOC_EXTRACT,        // 信息提取

    // 图表相关
    CHART_DRAW,         // 图表绘制
    DATA_ANALYZE,       // 数据分析

    // 部署相关
    DEPLOY,             // 部署
    ROLLBACK,           // 回滚

    // 调试相关
    DEBUG,              // 调试
    TEST,               // 测试

    // 其他
    UNKNOWN              // 未知意图
}
```

### 4.4 任务路由设计

```java
/**
 * 任务路由器
 * 职责: 根据意图类型，路由到对应的 Agent
 */
public class TaskRouter {

    private final Map<IntentType, AgentType> intentToAgentMap;

    /**
     * 路由到对应的 Agent
     */
    public AgentRoute route(IntentRecognitionResult intent, ExecutionStep step) {

        // 基于意图类型的路由
        AgentType agentType = switch (intent.getIntent()) {
            case CODE_GEN, CODE_FIX, CODE_REFACTOR -> AgentType.CODE_AGENT;
            case DOC_ANALYZE, DOC_SUMMARIZE, DOC_EXTRACT -> AgentType.DOC_AGENT;
            case CHART_DRAW, DATA_ANALYZE -> AgentType.CHART_AGENT;
            case DEPLOY -> AgentType.DEPLOY_AGENT;
            case DEBUG -> AgentType.DEBUG_AGENT;
            case TEST -> AgentType.TEST_AGENT;
            default -> AgentType.CODE_AGENT;  // 默认
        };

        return AgentRoute.builder()
            .agentType(agentType)
            .step(step)
            .executeInPython(true)  // Python 无状态执行
            .build();
    }
}
```

### 4.6 Agent 切换条件

```java
/**
 * Agent 切换决策器
 * 职责: 决定何时从一个 Agent 切换到另一个 Agent
 */
public class AgentSwitchDecisionMaker {

    /**
     * 判断是否需要切换 Agent
     */
    public SwitchDecision shouldSwitch(AgentExecutionContext context) {

        // 条件 1: 当前 Agent 任务完成
        if (context.getCurrentStep().isCompleted()) {
            return SwitchDecision.switchTo(context.getNextStep().getAgentType());
        }

        // 条件 2: 遇到无法处理的错误
        if (context.getLastError() != null &&
            context.getLastError().isUnrecoverable()) {
            // 切换到 FixAgent 或 DebugAgent
            return SwitchDecision.switchTo(AgentType.FIX_AGENT);
        }

        // 条件 3: 用户干预
        if (context.hasUserIntervention()) {
            UserIntervention intervention = context.getUserIntervention();
            return handleUserIntervention(intervention);
        }

        // 条件 4: 需要其他 Agent 的能力
        if (requiresOtherAgent(context)) {
            return decideTargetAgent(context);
        }

        // 条件 5: 执行时间/Token 超限
        if (exceedsLimits(context)) {
            return handleLimitExceeded(context);
        }

        return SwitchDecision.continueCurrent();
    }

    /**
     * Agent 切换触发条件
     */
    public enum SwitchTrigger {
        // 自然完成
        STEP_COMPLETE,
        PLAN_COMPLETE,

        // 错误触发
        UNRECOVERABLE_ERROR,
        TIMEOUT,

        // 用户触发
        USER_REQUEST,
        USER_FEEDBACK,

        // 系统触发
        TOKEN_LIMIT_EXCEEDED,
        CAPABILITY_MISMATCH,
        DEPENDENCY_READY
    }
}
```

### 5.1 设计目标

参考 Claude Code 的上下文管理机制，采用 **"主动工具调用 + 智能定位"** 策略：

| 问题 | 当前方案 | 新方案 |

| **上下文浪费** | 前3文件全量传递 | 主动工具调用，按需读取 |

| **依赖对话记忆** | 对话过长时丢失上下文 | 不依赖记忆，直接读取当前文件状态 |
| **文件变更感知** | 无 | Merkle Tree 快速检测 |

### 5.3 Token 预算管理

```java
/**
 * Token 预算分配策略
 */
public class TokenBudgetManager {

    // 模型 Token 限制
    private final int modelMaxTokens;  // 如 GPT-4: 8192

    // 系统提示预算
    private final int systemPromptTokens;

    // 预算分配比例
    private static final double METADATA_RATIO = 0.02;     // 2%
    private static final double SUMMARY_RATIO = 0.15;       // 15%
    private static final double RELEVANT_CODE_RATIO = 0.53; // 53%
    private static final double DETAILED_FILES_RATIO = 0.30; // 30%

    /**
     * 计算各层级的 Token 预算
     */
    public BudgetAllocation allocateBudget(int totalBudget) {

        int availableForContext = totalBudget - systemPromptTokens;

        return BudgetAllocation.builder()
            .metadata((int)(availableForContext * METADATA_RATIO))
            .structureSummary((int)(availableForContext * SUMMARY_RATIO))
            .relevantCode((int)(availableForContext * RELEVANT_CODE_RATIO))
            .detailedFiles((int)(availableForContext * DETAILED_FILES_RATIO))
            .build();
    }

    /**
     * 动态调整预算 (根据查询复杂度)
     */
    public BudgetAllocation adjustBudget(QueryComplexity complexity) {
        return switch (complexity) {
            case SIMPLE -> allocateBudget(totalBudget);  // 默认分配
            case MODERATE -> {
                // 中等复杂度: 减少摘要，增加相关代码
                return BudgetAllocation.builder()
                    .metadata((int)(available * 0.02))
                    .structureSummary((int)(available * 0.10))  // 减少
                    .relevantCode((int)(available * 0.60))  // 增加
                    .detailedFiles((int)(available * 0.28))
                    .build();
            }
            case COMPLEX -> {
                // 高复杂度: 最小化摘要，最大化相关代码
                return BudgetAllocation.builder()
                    .metadata((int)(available * 0.02))
                    .structureSummary((int)(available * 0.05))  // 最小化
                    .relevantCode((int)(available * 0.70))  // 最大化
                    .detailedFiles((int)(available * 0.23))
                    .build();
            }
        };
    }
}
```

## 六、Skill 机制设计

### 6.1 设计目标

参考 **Claude Code Skills** 和 **Cursor AI Skills**，引入 **可复用的能力单元**：

| 特性 | 说明 |
|------|------|
| **能力复用** | 常用操作封装成 Skill，可重复调用 |
| **参数化** | Skill 支持可配置参数 |
| **组合性** | 多个 Skill 可组合成 Workflow |
| **系统内置** | 系统提供常用 Skills |
| **用户自定义** | 用户可创建自己的 Skills |
| **版本管理** | Skill 支持版本控制和评分 |
| **使用统计** | 记录 Skill 使用次数和效果 |

### 6.2 Skill 分类

| Skill 类型 | 说明 | 示例 |
|-----------|------|------|
| **CodeSkill** | 代码生成 | 创建 Vue 组件、生成 API 接口、添加路由 |
| **DeploySkill** | 部署相关 | 构建 Docker 镜像、部署到 Vercel |
| **DocSkill** | 文档处理 | 解析 Excel、生成 PDF、提取文档摘要 |
| **ChartSkill** | 图表相关 | 生成折线图、创建数据透视表 |
| **GitSkill** | Git 操作 | 创建分支、提交代码、创建 PR |
| **TestSkill** | 测试相关 | 运行单元测试、生成测试数据 |

## 七、增量写入机制设计

### 7.1 设计目标

参考 **Cursor AI** 的增量编辑和 **Claude Code** 的精准修改策略，引入 **增量写入机制**：

| 问题 | 全量写入 | 增量写入 |
|------|---------|---------|
| **Token 消耗** | 发送整个文件内容 | 只发送变更行 + 上下文 |
| **大文件处理** | 超过上下文限制无法处理 | 支持任意大小文件 |
| **变更追踪** | 无法追踪具体变更 | 精准记录每行变更 |
| **冲突处理** | 全量覆盖可能丢失修改 | 检测冲突并提示用户 |
| **追溯能力** | 无法追溯变更来源 | 记录每个变更的 traceId |

### 7.4 Java 侧变更检测

```java
/**
 * 文件变更检测器
 * 负责比较新旧文件，生成增量变更
 */
@Component
public class FileChangeDetector {

    private static final int CONTEXT_LINES = 3;
    private static final int MAX_CHANGES_PER_FILE = 100;

    /**
     * 检测文件变更
     *
     * @param oldContent 原文件内容
     * @param newContent 新文件内容
     * @param filePath 文件路径
     * @param traceId 追溯 ID
     * @return 变更结果
     */
    public FileChangeResult detectChanges(
            String oldContent,
            String newContent,
            String filePath,
            String traceId) {

        List<LineChange> changes = new ArrayList<>();

        // 分行
        String[] oldLines = oldContent.split("\n", -1);
        String[] newLines = newContent.split("\n", -1);

        // 使用 Myers Diff 算法检测变更
        List<DiffEntry> diffs = computeMyersDiff(oldLines, newLines);

        // 转换为 LineChange
        int oldLineNum = 1;
        int newLineNum = 1;

        for (DiffEntry diff : diffs) {
            switch (diff.getType()) {
                case DELETE:
                    changes.add(createDeletion(
                        oldLineNum,
                        oldLines[oldLineNum - 1],
                        getContext(oldLines, oldLineNum, CONTEXT_LINES),
                        traceId
                    ));
                    oldLineNum++;
                    break;

                case INSERT:
                    changes.add(createAddition(
                        newLineNum,
                        newLines[newLineNum - 1],
                        getContext(oldLines, oldLineNum - 1, CONTEXT_LINES),
                        traceId
                    ));
                    newLineNum++;
                    break;

                case EQUAL:
                    oldLineNum++;
                    newLineNum++;
                    break;
            }
        }

        return FileChangeResult.builder()
            .filePath(filePath)
            .changes(changes)
            .summary(generateSummary(changes))
            .hasConflict(false)  // 冲突检测在合并阶段进行
            .changedAt(LocalDateTime.now())
            .build();
    }

    /**
     * Myers Diff 算法实现
     */
    private List<DiffEntry> computeMyersDiff(String[] oldLines, String[] newLines) {
        // 使用 java-diff 库或自行实现
        // 这里简化为伪代码
        return MyersDiff.diff(oldLines, newLines);
    }

    /**
     * 获取上下文
     */
    private List<String> getContext(String[] lines, int centerLine, int contextLines) {
        int start = Math.max(0, centerLine - contextLines);
        int end = Math.min(lines.length, centerLine + contextLines);
        return Arrays.asList(Arrays.copyOfRange(lines, start, end));
    }

    /**
     * 生成变更摘要
     */
    private String generateSummary(List<LineChange> changes) {
        long additions = changes.stream()
            .filter(c -> c.getType() == LineChangeType.ADDITION)
            .count();
        long deletions = changes.stream()
            .filter(c -> c.getType() == LineChangeType.DELETION)
            .count();
        long modifications = changes.stream()
            .filter(c -> c.getType() == LineChangeType.MODIFICATION)
            .count();

        return String.format("+%d行, -%d行, ~%d行",
            additions, deletions, modifications);
    }
}

/**
 * 增量上下文构建器
 * 为 AI 生成提供精准的上下文
 */
@Component
public class IncrementalContextBuilder {

    @Autowired
    private FileChangeDetector changeDetector;

    /**
     * 构建增量上下文
     *
     * @param oldContent 原文件内容
     * @param newContent 新文件内容
     * @param filePath 文件路径
     * @param traceId 追溯 ID
     * @return 增量上下文（JSON 格式）
     */
    public IncrementalWriteContext buildContext(
            String oldContent,
            String newContent,
            String filePath,
            String traceId) {

        // 检测变更
        FileChangeResult changeResult = changeDetector.detectChanges(
            oldContent, newContent, filePath, traceId);

        // 构建 AI 需要的上下文
        return IncrementalWriteContext.builder()
            .file(filePath)
            .oldFileHash(computeHash(oldContent))
            .newFileHash(computeHash(newContent))
            .totalLines(oldContent.split("\n").length)
            .changesCount(changeResult.getChanges().size())
            .changes(buildChangeContexts(changeResult))
            .summary(changeResult.getSummary())
            .build();
    }

    /**
     * 构建每个变更的上下文
     */
    private List<ChangeContext> buildChangeContexts(FileChangeResult result) {
        return result.getChanges().stream()
            .map(this::buildSingleChangeContext)
            .collect(Collectors.toList());
    }

    /**
     * 构建单个变更的上下文
     */
    private ChangeContext buildSingleChangeContext(LineChange change) {
        return ChangeContext.builder()
            .type(change.getType())
            .lineNumber(change.getLineNumber())
            .contextBefore(change.getContextBefore())
            .contextAfter(change.getContextAfter())
            // 对于 MODIFICATION，同时发送新旧内容
            .oldLine(change.getOldContent())
            .newLine(change.getNewContent())
            .build();
    }

    private String computeHash(String content) {
        // SHA-256 哈希
        return DigestUtils.sha256Hex(content);
    }
}
```

### 7.5 Python 侧增量写入工具

```python
"""
增量写入工具
接收 Java 传递的增量变更，应用到文件
"""
from typing import List, Dict, Any
from pathlib import Path
import hashlib

app/tools/code/
├── __init__.py
├── incremental_write_tool.py    # 增量写入工具
├── file_read_tool.py
└── deploy_tool.py


class IncrementalWriteTool(BaseTool):
    """增量写入工具"""

    name = "incremental_write"
    description = "增量写入文件，只写入变更的部分"

    def __init__(self):
        super().__init__()
        self.change_detector = ChangeDetector()
        self.conflict_resolver = ConflictResolver()

    async def execute(self, context: IncrementalWriteContext) -> WriteResult:
        """
        执行增量写入

        Args:
            context: 增量写入上下文

        Returns:
            写入结果
        """
        file_path = Path(context.file)

        # 1. 读取原文件
        original_content = file_path.read_text() if file_path.exists() else ""
        original_lines = original_content.split("\n") if original_content else []

        # 2. 验证文件哈希（防止并发修改）
        if context.old_file_hash:
            current_hash = hashlib.sha256(original_content.encode()).hexdigest()
            if current_hash != context.old_file_hash:
                # 文件已被修改，需要合并或通知用户
                return await self._handle_conflict(context, original_content)

        # 3. 应用变更
        new_lines = self._apply_changes(original_lines, context.changes)

        # 4. 写入文件
        new_content = "\n".join(new_lines)
        file_path.write_text(new_content)

        # 5. 验证新文件哈希
        new_hash = hashlib.sha256(new_content.encode()).hexdigest()
        if new_hash != context.new_file_hash:
            # 哈希不匹配，可能有问题
            logger.warning(f"Hash mismatch after write: {new_hash} != {context.new_file_hash}")

        return WriteResult(
            success=True,
            file=str(file_path),
            lines_added=sum(1 for c in context.changes if c.type == "ADDITION"),
            lines_deleted=sum(1 for c in context.changes if c.type == "DELETION"),
            lines_modified=sum(1 for c in context.changes if c.type == "MODIFICATION"),
            trace_id=context.trace_id
        )

    def _apply_changes(
        self,
        original_lines: List[str],
        changes: List[ChangeContext]
    ) -> List[str]:
        """
        应用变更到原始行

        按行号从大到小处理，避免索引错位
        """
        result = original_lines.copy()

        sorted_changes = sorted(
            [c for c in changes if c.type != "EQUAL"],
            key=lambda x: x.line_number,

        for change in sorted_changes:

            if change.type == "ADDITION":

                result.insert(line_idx, change.new_line)
            elif change.type == "DELETION":
                # 删除行
                if line_idx < len(result):
                    result.pop(line_idx)
            elif change.type == "MODIFICATION":
                # 修改行
                if line_idx < len(result):
                    result[line_idx] = change.new_line

    def detect(self, old: str, new: str) -> List[Dict[str, Any]]:
        """
        检测两个文本的差异

        使用 difflib.SequenceMatcher
        """
        import difflib

        old_lines = old.split("\n")
        new_lines = new.split("\n")

        matcher = difflib.SequenceMatcher(None, old_lines, new_lines)
        changes = []

        for tag, i1, i2, j1, j2 in matcher.get_opcodes():
            if tag == "replace":
                changes.append({
                    "type": "MODIFICATION",
                    "lineNumber": i1 + 1,
                    "oldLines": old_lines[i1:i2],
                    "newLines": new_lines[j1:j2]
                })
            elif tag == "delete":
                changes.append({
                    "type": "DELETION",
                    "lineNumber": i1 + 1,
                    "oldLines": old_lines[i1:i2]
                })
            elif tag == "insert":
                changes.append({
                    "type": "ADDITION",
                    "lineNumber": i1 + 1,
                    "newLines": new_lines[j1:j2]
                })

        return changes
```

```java
        // 1. 分析任务复杂度
        TaskComplexity complexity = complexityAnalyzer.analyze(task);

        // 2. 获取用户偏好（如果有）
        Optional<LlmLevel> userPreferred = preference.getPreferredLevel();

        // 3. 考虑配额限制
        LlmLevel availableLevel = checkQuota(complexity, userPreferred);

        // 4. 选择具体模型
        LlmModel selected = llmRegistry.getBestModel(availableLevel, task);

        // 5. 记录决策
        logRoutingDecision(task, complexity, selected);

        return LlmSelection.builder()
            .model(selected)
            .reason(getReason(complexity, selected))
            .estimatedCost(estimateCost(task, selected))
            .estimatedDuration(estimateDuration(task, selected))
            .build();
    }

    /**
     * 检查配额并决定可用级别
     */
    private LlmLevel checkQuota(TaskComplexity complexity, Optional<LlmLevel> preferred) {
        UserQuota quota = usageMetrics.getUserQuota();

        // 用户有明确偏好且配额足够
        if (preferred.isPresent() && quota.canUse(preferred.get())) {
            return preferred.get();
        }

        // 根据复杂度和剩余配额决定
        if (quota.getL3Remaining() > 0 && complexity.isHigh()) {
            return LlmLevel.L3_OPUS;
        } else if (quota.getL2Remaining() > 0) {
            return LlmLevel.L2_SONNET;
        } else {
            return LlmLevel.L1_HAIKU;
        }
    }

    /**

     */
    @Component
    public static class TaskComplexityAnalyzer {

        public TaskComplexity analyze(AgentTask task) {
            int score = 0;

            // 文件数量
            score += calculateFileCountScore(task.getFileCount());

            // 代码行数
            score += calculateLineCountScore(task.getTotalLines());

            // 任务类型
            score += getTaskTypeScore(task.getType());

            // 依赖关系
            score += calculateDependencyScore(task.getDependencies());

            // 是否需要跨文件修改
            if (task.isCrossFile()) {
                score += 20;
            }

            return TaskComplexity.fromScore(score);
        }

        private int calculateFileCountScore(int fileCount) {
            if (fileCount <= 1) return 0;
            if (fileCount <= 5) return 10;
            if (fileCount <= 10) return 25;
            return 40;
        }

        private int calculateLineCountScore(int lines) {
            if (lines <= 100) return 0;
            if (lines <= 500) return 10;
            if (lines <= 2000) return 20;
            return 30;

        private int getTaskTypeScore(TaskType type) {

                case CODE_FORMAT -> 5;
                case CODE_GENERATION -> 20;

                case DEBUGGING -> 40;
```

```java
/**
 * 大模型降级管理器
 * 处理模型故障、超时、配额不足等场景
 */
@Component
public class LlmFallbackManager {

    @Autowired
    private LlmRegistry llmRegistry;

    @Autowired
    private CircuitBreakerRegistry circuitBreakerRegistry;

    /**
     * 执行带降级的 LLM 调用
     */
    public <T> T executeWithFallback(
            LlmSelection selection,
            Function<LlmModel, T> primaryCall,
            Function<LlmModel, T> fallbackCall) {

        LlmModel primary = selection.getModel();
        CircuitBreaker circuitBreaker = circuitBreakerRegistry.circuitBreaker(primary.getName());

        // 检查熔断器状态
        if (circuitBreaker.tryAcquirePermission()) {
            try {
                T result = primaryCall.apply(primary);
                circuitBreaker.onSuccess();
                return result;
            } catch (Exception e) {
                circuitBreaker.onError(e);
                log.error("Primary LLM failed: {}", e.getMessage());

                // 尝试降级
                return executeFallback(selection, fallbackCall);
            }
        } else {
            // 熔断器打开，直接降级
            log.warn("Circuit breaker open for {}, using fallback", primary.getName());
            return executeFallback(selection, fallbackCall);
        }
    }

    /**
     * 执行降级调用
     */
    private <T> T executeFallback(LlmSelection selection, Function<LlmModel, T> fallbackCall) {
        // 获取降级模型
        LlmModel fallback = llmRegistry.getFallbackModel(selection.getModel());

        log.info("Using fallback model: {} -> {}",
            selection.getModel().getName(), fallback.getName());

        try {
            return fallbackCall.apply(fallback);
        } catch (Exception e) {
            // 再降级一次
            LlmModel lastResort = llmRegistry.getFallbackModel(fallback);
            return fallbackCall.apply(lastResort);
        }
    }
}
```

```java
    private Integer l3UsedToday = 0;

    // 重置时间
    private LocalDateTime lastResetDate;

    @Transient
    public boolean canUse(LlmLevel level) {
        resetIfNeeded();
        return switch (level) {
            case L1_HAIKU -> l1UsedToday < l1DailyLimit;
            case L2_SONNET -> l2UsedToday < l2DailyLimit;
            case L3_OPUS -> l3UsedToday < l3DailyLimit;
        };
    }

    private void resetIfNeeded() {
        LocalDateTime now = LocalDateTime.now();
        if (lastResetDate == null || lastResetDate.toLocalDate().isBefore(now.toLocalDate())) {
            l1UsedToday = 0;
            l2UsedToday = 0;
            l3UsedToday = 0;
            lastResetDate = now;
        }
    }
}
```

### 9.4 回退管理器

```java
/**
 * 代码回退管理器
 * 提供版本回退、切换、对比等功能
 */
@Service
public class CodeRollbackManager {

    @Autowired
    private CodeVersionSnapshotRepository snapshotRepository;

    @Autowired
    private FileChangeDetector changeDetector;

    @Autowired
    private IncrementalWriteTraceService traceService;

    /**
     * 回退到指定版本
     */
    public RollbackResult rollbackTo(String snapshotId, String reason, Long userId) {
        CodeVersionSnapshot target = snapshotRepository.findBySnapshotId(snapshotId)
            .orElseThrow(() -> new SnapshotNotFoundException(snapshotId));

        // 1. 获取当前版本
        CodeVersionSnapshot current = snapshotRepository.findCurrentVersion(
            target.getAppId(), target.getFilePath())
            .orElseThrow();

        // 2. 记录当前版本为回退前状态
        current.setRolledBack(true);
        current.setRolledBackAt(LocalDateTime.now());
        snapshotRepository.save(current);

        // 3. 创建回退快照（标记为回退点）
        CodeVersionSnapshot rollbackPoint = createRollbackPoint(current, target, reason);
        snapshotRepository.save(rollbackPoint);

        // 4. 计算变更（当前 → 目标）
        FileChangeResult changes = calculateChanges(current, target);

        // 5. 应用变更
        applyChanges(changes, target.getFilePath());

        // 6. 更新目标版本为当前
        target.setCurrent(true);
        current.setCurrent(false);
        snapshotRepository.save(target);

        // 7. 记录追溯
        traceService.logRollback(current.getSnapshotId(), target.getSnapshotId(),
            reason, userId);

        return RollbackResult.builder()
            .success(true)
            .fromSnapshotId(current.getSnapshotId())
            .toSnapshotId(target.getSnapshotId())
            .changesCount(changes.getChanges().size())
            .summary(changes.getSummary())
            .build();
    }

    /**
     * 创建回退点快照
     */
    private CodeVersionSnapshot createRollbackPoint(
            CodeVersionSnapshot current,
            CodeVersionSnapshot target,
            String reason) {

        return CodeVersionSnapshot.builder()
            .snapshotId(generateSnapshotId())
            .taskId(current.getTaskId())
            .appId(current.getAppId())
            .userId(current.getUserId())
            .filePath(current.getFilePath())
            .fileType(current.getFileType())
            .fullContent(current.getFullContent())
            .contentHash(current.getContentHash())
            .parentSnapshotId(current.getSnapshotId())
            .branchName("rollback/" + current.getSnapshotId())
            .status(SnapshotStatus.COMMITTED)
            .isCurrent(false)
            .isRolledBack(true)
            .rollbackReason(reason)
            .createdAt(LocalDateTime.now())
            .build();
    }

    /**
     * 对比两个版本
     */
    public VersionDiffResult compareVersions(String snapshotId1, String snapshotId2) {
        CodeVersionSnapshot v1 = snapshotRepository.findBySnapshotId(snapshotId1).get();
        CodeVersionSnapshot v2 = snapshotRepository.findBySnapshotId(snapshotId2).get();

        FileChangeResult changes = changeDetector.detectChanges(
            v1.getFullContent(),
            v2.getFullContent(),
            v1.getFilePath(),
            "diff_" + snapshotId1 + "_" + snapshotId2
        );

        return VersionDiffResult.builder()
            .snapshotId1(snapshotId1)
            .snapshotId2(snapshotId2)
            .changes(changes.getChanges())
            .summary(changes.getSummary())
            .v1Info(VersionInfo.from(v1))
            .v2Info(VersionInfo.from(v2))
            .build();
    }

    /**
     * 获取版本历史
     */
    public List<VersionHistoryItem> getHistory(String filePath, Long appId) {
        List<CodeVersionSnapshot> snapshots = snapshotRepository
            .findByAppIdAndFilePathOrderByCreatedAtDesc(appId, filePath);

        return snapshots.stream()
            .map(VersionHistoryItem::from)
            .collect(Collectors.toList());
    }
}
```

### 9.5 修改机制

```java
/**
 * 代码修改管理器
 * 支持基于快照的精确修改
 */
@Service
public class CodeModificationManager {

    @Autowired
    private CodeVersionSnapshotRepository snapshotRepository;

    @Autowired
    private LlmRouter llmRouter;

    /**
     * 基于快照进行修改
     */
    public ModificationResult modifyFromSnapshot(
            String baseSnapshotId,
            UserModificationRequest request,
            Long userId) {

        // 1. 获取基础版本
        CodeVersionSnapshot base = snapshotRepository.findBySnapshotId(baseSnapshotId)
            .orElseThrow();

        // 2. 创建新快照（基于基础版本）
        String newSnapshotId = generateSnapshotId();
        CodeVersionSnapshot newSnapshot = createNewSnapshot(base, newSnapshotId, request);
        snapshotRepository.save(newSnapshot);

        // 3. 构建修改任务
        AgentTask task = AgentTask.builder()
            .type(TaskType.CODE_MODIFICATION)
            .baseSnapshotId(baseSnapshotId)
            .userRequest(request.getInstruction())
            .targetSnapshotId(newSnapshotId)
            .file(base.getFilePath())
            .baseContent(base.getFullContent())
            .build();

        // 4. 选择合适的 LLM
        LlmSelection selection = llmRouter.selectLlm(task, request.getUserPreference());

        // 5. 执行修改
        ModificationExecutionResult execution = executeModification(task, selection);

        // 6. 保存新版本
        newSnapshot.setFullContent(execution.getNewContent());
        newSnapshot.setContentHash(computeHash(execution.getNewContent()));
        newSnapshot.setStatus(SnapshotStatus.COMMITTED);
        newSnapshot.setCurrent(true);

        // 基础版本不再为当前
        base.setCurrent(false);
        snapshotRepository.save(base);

        return ModificationResult.builder()
            .success(execution.isSuccess())
            .snapshotId(newSnapshotId)
            .changes(execution.getChanges())
            .llmUsed(selection.getModel().getId())
            .tokensUsed(execution.getTokensUsed())
            .durationMs(execution.getDurationMs())
            .build();
    }

    /**
     * 修改建议预览
     */
    public ModificationPreview previewModification(
            String baseSnapshotId,
            String instruction,
            Long userId) {

        CodeVersionSnapshot base = snapshotRepository.findBySnapshotId(baseSnapshotId).get();

        // 使用 L1 模型快速分析
        LlmModel lightweightModel = llmRouter.getLightweightModel();

        PreviewAnalysisResult analysis = analyzeModification(
            base.getFullContent(),
            instruction,
            lightweightModel
        );

        return ModificationPreview.builder()
            .baseSnapshotId(baseSnapshotId)
            .filePath(base.getFilePath())
            .estimatedChanges(analysis.getEstimatedChanges())
            .estimatedComplexity(analysis.getComplexity())
            .estimatedCost(analysis.getEstimatedCost())
            .suggestedSkills(analysis.getSuggestedSkills())
            .build();
    }

    /**
     * 批量修改
     */
    public BatchModificationResult batchModify(
            List<String> snapshotIds,
            String instruction,
            Long userId) {

        List<ModificationResult> results = new ArrayList<>();
        int success = 0;
        int failed = 0;

        for (String snapshotId : snapshotIds) {
            try {
                UserModificationRequest request = UserModificationRequest.builder()
                    .instruction(instruction)
                    .build();

                ModificationResult result = modifyFromSnapshot(snapshotId, request, userId);
                results.add(result);

                if (result.isSuccess()) {
                    success++;
                } else {
                    failed++;
                }
            } catch (Exception e) {
                failed++;
                results.add(ModificationResult.failed(snapshotId, e.getMessage()));
            }
        }

        return BatchModificationResult.builder()
            .totalCount(snapshotIds.size())
            .successCount(success)
            .failedCount(failed)
            .results(results)
            .build();
    }
}
```

### 6.3 数据库设计

```sql
-- 通用数据存储表
CREATE TABLE data_store (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    -- 归属
    app_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    collection_name VARCHAR(100) NOT NULL,

    -- 数据
    data_key VARCHAR(255) NOT NULL,
    data_value JSON NOT NULL,

    -- 元数据
    version INT DEFAULT 1,
    tags JSON,
    indexes JSON,

    -- 时间
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW() ON UPDATE NOW(),
    expires_at TIMESTAMP NULL,

    -- 软删除
    deleted BOOLEAN DEFAULT FALSE,

    -- 索引
    UNIQUE KEY uk_app_collection_key (app_id, collection_name, data_key, deleted),
    INDEX idx_collection (app_id, collection_name),
    INDEX idx_created (created_at)
);

-- 应用配额表 (限流控制)
CREATE TABLE app_quota (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    app_id BIGINT NOT NULL UNIQUE,

    -- 限流配置
    max_records INT DEFAULT 10000,
    max_storage_mb INT DEFAULT 100,

    -- 当前使用量
    current_records INT DEFAULT 0,
    current_storage_mb INT DEFAULT 0,

    -- 时间
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW() ON UPDATE NOW(),

    INDEX idx_app_id (app_id)
);
```

### 6.4 安全验证方案

```
┌───────────────────────────────────────────────────────────────────────┐
│                        BaaS 安全验证流程                              │
│                                                                     │
│  前端请求                                                           │
│    POST /api/baas/data/create                                         │
│    Header: Authorization: Bearer <用户JWT>                            │
│    Header: X-App-Id: <应用ID>                                       │
│    Body: { collection: "users", data: {...} }                        │
│         ↓                                                          │
│  ┌───────────────────────────────────────────────────────────────┐   │
│  │  第一步：验证用户身份                                        │   │
│  │  - 解析 JWT Token                                             │   │
│  │  - 检查 Token 是否过期                                        │   │
│  │  - 提取 userId                                                 │   │
│  └───────────────────────────────────────────────────────────────┘   │
│         ↓                                                          │
│  ┌───────────────────────────────────────────────────────────────┐   │
│  │  第二步：验证应用权限                                        │   │
│  │  - 检查用户是否有权访问该应用 (app_id belongs to user_id)    │   │
│  │  - 检查应用状态是否正常                                       │   │
│  └───────────────────────────────────────────────────────────────┘   │
│         ↓                                                          │
│  ┌───────────────────────────────────────────────────────────────┐   │
│  │  第三步：检查配额限流                                        │   │
│  │  - 检查应用数据条数是否超限                                  │   │
│  │  - current_records < max_records                             │   │
│  │  - 超限返回错误，提示升级套餐                                    │   │
│  └───────────────────────────────────────────────────────────────┘   │
│         ↓                                                          │
│  ┌───────────────────────────────────────────────────────────────┐   │
│  │  第四步：数据权限隔离                                        │   │
│  │  - WHERE app_id = ? AND user_id = ? AND deleted = false           │   │
│  │  - 确保用户只能访问自己应用的数据                              │   │
│  └───────────────────────────────────────────────────────────────┘   │
│         ↓                                                          │
│  执行数据操作                                                         │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 6.5 限流策略

| 限制类型 | 默认值 | 说明 |
|---------|---------|------|
| **单应用数据条数** | 10,000 条 | 每个应用最多存储 1 万条数据 |
| **单条数据大小** | 1 MB | 单个 JSON 数据最大 1MB |
| **单应用总存储** | 100 MB | 所有数据总大小限制 |
| **查询返回条数** | 100 条 | 单次查询最多返回 100 条 |
| **请求频率限制** | 100 次/分钟 | 单个应用的请求频率 |

### 11.2 指数退避 (Exponential Backoff)

**原理**：每次重试的等待时间呈指数增长，避免雪崩

```
重试次数：    1     2     3     4     5
等待时间：    1s    2s    4s    8s    16s

公式：wait_time = base_delay * (2 ^ (retry_count - 1))
      = 1000ms * (2 ^ (3 - 1))
      = 1000ms * 4
      = 4000ms
```

**带抖动的指数退避（大厂常用）**：

```
wait_time = (base_delay * (2 ^ (retry_count - 1))) + random_jitter()

示例：
重试1：1000ms + random(0, 200)ms  = 1150ms
重试2：2000ms + random(0, 400)ms  = 2100ms
重试3：4000ms + random(0, 800)ms  = 4500ms

好处：避免多个客户端同时重试，造成"惊群效应"
```

### 11.3 幂等性设计 (Idempotency)

**问题**：重试可能导致重复执行

```
场景：用户支付
第一次请求：扣款 100 元 → 网络超时 → 状态未知
第二次重试：扣款 100 元 → 成功
结果：用户被扣了 200 元！
```

**解决方案**：每个请求携带幂等 Key

```
┌─────────────────────────────────────────────────────────────────────┐
│                    幂等性设计                               │
│                                                             │
│  客户端请求                                                    │
│    POST /api/v1/agent-run                                        │
│    Header: X-Idempotent-Key: <uuid>                          │
│    Body: {...}                                                │
│         ↓                                                    │
│  ┌───────────────────────────────────────────────────┐   │
│  │  服务端                                                │   │
│  │  1. 检查 Redis: idempotent:<key>                     │   │
│  │      - 存在 → 返回缓存结果（5分钟）              │   │
│  │      - 不存在 → 执行请求，缓存结果                      │   │
│  └───────────────────────────────────────────────────┘   │
│         ↓                                                    │
│  返回结果                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 11.4 断路器模式 (Circuit Breaker)

**原理**：当错误率达到阈值时，暂时停止请求，快速失败

```
正常状态 (Closed)
    ↓
连续失败达到阈值
    ↓
熔断状态 (Open) → 50秒内所有请求快速失败
    ↓
50秒后进入半开状态 (Half-Open)
    ↓
放行一个请求探测 → 成功则恢复正常，失败则继续熔断
    ↓
恢复正常状态 (Closed)
```


## 二十、架构对比

### 16.1 与当前架构对比

| 方面 | 当前架构 | 新架构 |
|------|---------|--------|
| **代码生成模式** | 固定 Pipeline (责任链) | Agent 编排 + Plan Mode |
| **AI 逻辑位置** | Java (LangChain4j) | Python (无状态服务) |
| **配置管理** | Java 硬编码 | Java 统一管理，JWT 传递 |
| **扩展性** | 添加 Handler | 添加 Agent/Tool |
| **追溯能力** | 无 | 全链路 traceId 追溯 |
| **数据接口** | 无 | BaaS 通用数据接口 |
| **支持能力** | 代码生成 | 代码 + 文档 + 图表 |
| **上下文管理** | 前3文件全量 | 四级分级 + Merkle Tree |

### 16.2 关键改进

| 改进点 | 说明 |
|--------|------|
| **Java 负责编排** | 意图识别、任务路由、Agent 切换均在 Java 侧 |
| **配置安全** | 所有密钥由 Java 管理，Python 无状态 |
| **全链路追溯** | 每个事件都有 traceId，可完整追踪 |
| **通用架构** | 支持代码、文档、图表等多种任务 |
| **错误重试** | 指数退避 + 幂等性 + SSE 回放 |
| **全新上下文管理** | 四级分级 + Merkle Tree + Token 精准分配 |
| **易于扩展** | 新增能力只需添加 Agent 和 Tool |
| **职责清晰** | Java 管业务和状态，Python 执行 AI 逻辑 |

### 16.3 技术亮点

| 亮点 | 说明 |
|------|------|
| **Plan Mode** | 执行前展示计划，用户确认后再执行 |
| **四级上下文** | 元数据 → 结构摘要 → 相关代码 → 详细内容 |
| **Merkle Tree** | 快速检测文件变更，增量更新索引 |
| **Token 精准分配** | 根据查询复杂度动态调整预算 |
| **Agent 协作** | 支持顺序、并行、协作、层级四种模式 |
| **SSE 断线恢复** | 事件回放机制，保证体验连续性 |
